# Squadz Load-Test Suite

## Part 1 — Transaction-Pooler Privacy Audit

**Result: CLEAN. No changes required.**

Audit performed across the full `artifacts/api-server` and `lib/db` source trees:

| Check | Result |
|---|---|
| Raw `SET` (non-LOCAL) SQL in app code | ✅ None found — no `db.execute(sql\`SET ...\`)` or `pool.query("SET ...")` in any route or lib |
| `SET search_path`, `SET statement_timeout`, `SET work_mem`, etc. | ✅ None in application code |
| Connection-level `options` string in pool config (`-c key=val`) | ✅ Not present — `resolveDbConfig()` returns only host/port/credentials/TLS/pool sizing |
| `pool.on("connect", ...)` callback issuing SET statements | ✅ Not present — no `pool.on("connect")` anywhere in application code |
| Advisory locks safe for Transaction pooler | ✅ All three usages (`squadLimit.ts`, `founding.ts`, `routes/events.ts`) use `pg_advisory_xact_lock` — transaction-scoped, released at COMMIT, safe for connection reuse |
| Pool singleton architecture | ✅ `lib/db/src/index.ts` creates one `Pool` and one `drizzle(pool)`. Drizzle calls `pool.query()` per query — connection is checked out and returned immediately, never held across requests |
| SSE handlers (5 SSE streams) | ✅ Hold an HTTP connection open; issue a single auth DB query before streaming begins, then use an in-memory event emitter + `setInterval` for heartbeats. No DB connection is held during the stream lifetime |
| `pool.connect()` / `pool.query()` in app routes | ✅ None — only in `src/__tests__/concurrency/` test harnesses and one-off backfill scripts in `scripts/` |

**Risk to cross-user data leakage under Transaction pooler: none identified.**

## Part 3 — Staging Target Assessment

**⚠️ No separate staging database exists. Do not run against production.**

The dev server at `$REPLIT_DEV_DOMAIN` shares the **same Supabase instance** as
production. Running a 100-VU load test against it would:
- Stress the production Supabase DB (shared pool, shared CPU)
- Pollute production with 100 test accounts (even if later cleaned up)
- Risk hitting the Supabase pooler connection cap and causing prod user 503s

**Before Part 3 can proceed, you need a safe target.** Options (in order of preference):

1. **New Supabase project for staging** — create a free Supabase project, set its
   `SUPABASE_DB_URL` in a separate Replit deployment (or a local `.env` override),
   and run the seed + Artillery test against that deployment's URL.

2. **Replit staging deployment** — deploy a second instance of the app pointing at
   the staging Supabase project. Run the load test against that deployment URL.

3. **Ephemeral local cluster** — extend `src/__tests__/concurrency/realDb.concurrency.test.ts`
   (which already spins up a local Postgres via `initdb`) to drive concurrent
   HTTP load. This tests DB/connection-pool behaviour without touching Supabase
   at all. It does NOT test TLS, network latency, or Supabase-specific pooler
   behaviour — but it is safe and requires no new infrastructure.

## Usage (once you have a staging target)

### 1. Install dependencies

```bash
# Artillery is already installed globally.
# Seed/cleanup scripts require tsx and @supabase/supabase-js.
pnpm add -D tsx
# @supabase/supabase-js should already be in api-server; if not:
pnpm --filter @workspace/api-server add @supabase/supabase-js
```

### 2. Seed test accounts

```bash
SUPABASE_URL=https://<staging-project>.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=<staging-service-role-key> \
LOAD_TEST_TARGET=https://<staging-api-url> \
npx tsx load-tests/seed.ts
```

This creates `load-tests/.test-accounts.csv` — 100 rows of `token,email,userId`.
Run this immediately before the load test (Supabase JWTs expire after 1 hour).

### 3. Run the load test

```bash
LOAD_TEST_TARGET=https://<staging-api-url> \
artillery run load-tests/squadz.yml
```

Phases:
| Phase | Duration | Arrivals/s | ≈ Concurrent sessions |
|---|---|---|---|
| Warm up | 30 s | 5/s | ~10 |
| Ramp | 60 s | 5 → 25/s | ~10 → 50 |
| Sustained | 60 s | 25/s | ~50 |
| Peak | 60 s | 50/s | ~100 |
| Sustain peak | 60 s | 50/s | ~100 |

Total: ~4.5 minutes.

**While the test runs** — watch the Supabase dashboard live:
- Database → Connection count (should stay below pooler max)
- Query Performance → slow queries
- CPU / memory on the Postgres instance

### 4. Interpret results

Artillery prints p50/p95/p99 per scenario at the end. Target thresholds:
| Metric | Target | Concern |
|---|---|---|
| p50 | < 200 ms | — |
| p95 | < 500 ms | > 1 s is degraded |
| p99 | < 1 s | > 3 s means queue buildup |
| Error rate | < 0.1% | > 1% needs investigation |

Key things to check at high concurrency:
- 429s from the DB-backed rate limiter (expected if a single IP fires >200 req/15min)
- 500s or timeouts from Supabase pool exhaustion
- Latency cliff between the 50-VU and 100-VU phases

### 5. Clean up test accounts

```bash
SUPABASE_URL=https://<staging-project>.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=<staging-service-role-key> \
npx tsx load-tests/cleanup.ts
```

### ⚠️ Login-endpoint load testing

The `POST /api/auth/login` endpoint is rate-limited to **20 requests per
15-minute window per source IP** (DB-backed, survives restarts). A load test
from a single IP will hit this limit within seconds at high concurrency. To
stress-test the login path you need multiple source IPs (e.g. Artillery on a
cloud runner, or multiple parallel runs from different machines). The current
Artillery config only tests authenticated read endpoints, not the login flow.
