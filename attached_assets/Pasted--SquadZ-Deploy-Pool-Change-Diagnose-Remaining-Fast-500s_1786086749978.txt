## Track B — Diagnose the fast application-level 500s (before attempting any fix)

The prior run found ~3.2% of requests failing fast (~207ms) on `/api/squads`, `/api/events`, `/api/feed`, or `/api/activity` — ruled out as pool timeouts based on response time alone.

1. **First, classify the bug type before fixing anything**: reproduce the same requests that failed during the load test, but at low/no concurrency (1 request at a time, no load). Do the same errors occur at all under normal single-user conditions, or only when many requests hit the same endpoint concurrently?
   - If the errors reproduce even at low concurrency: this is a pre-existing bug unrelated to scale, likely present in production right now regardless of load, and should be treated with the same urgency as any other correctness bug — not deprioritized as a "scale" issue.
   - If the errors only occur under concurrent load: this points to a race condition or shared-state issue specific to simultaneous requests (e.g. two requests hitting a resource at the same time in a way single-request testing wouldn't surface).
2. Once classified, identify the actual error by capturing full stack traces/error details from the failing requests during a reproduction (not just the fact that they fail) — check Sentry if these are already being captured there, since Sentry is already wired into the app per existing setup.
3. Report the root cause and a specific fix, gated on Steps 1-2 actually identifying what's failing — do not guess at a fix without first confirming the actual error.
