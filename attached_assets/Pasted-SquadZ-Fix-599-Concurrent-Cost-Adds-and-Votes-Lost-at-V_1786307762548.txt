SquadZ — Fix #599: Concurrent Cost-Adds and Votes Lost at Version 0
Context: task #592 surfaced two pre-existing failing real-DB concurrency tests (confirmed pre-existing by stashing #592’s work and re-running against baseline — not regressions). Both are the same lost-update class already fixed elsewhere: 5 concurrent cost-adds at version 0 and 5 concurrent votes at version 0 lose updates because the version-checked compare-and-swap is bypassed when the version is 0 (or absent). This is the same root pattern as the #575 version-bypass finding. Worth fixing now, before the cost-splitting feature (#583) gets built on this same path.
The problem
The version guard protects concurrent writes only when a meaningful version is present. At version 0 (initial/absent state), concurrent cost-adds or votes skip the guard and overwrite each other — a lost expense, a lost vote. The two real-DB tests filed under #599 already demonstrate this failing.
The fix
Apply the same atomic, version-safe pattern already used successfully in #592’s membership fixes to the cost-add and vote write paths:
	•	Concurrent writes at ANY version — including version 0 — must not silently overwrite each other.
	•	Use a compare-and-swap with re-read retry (the pattern #592 established for membership writes), or an atomic DB-level operation (e.g. atomic array append / jsonb operation) that doesn’t depend on a non-zero version to be safe. Choose whichever is most consistent with how these specific writes work and how #592 solved the analogous membership case.
	•	The end state: N concurrent cost-adds all land (none lost), and N concurrent votes all register correctly, regardless of starting version.
Verify with the already-failing tests
The two real-DB tests that currently fail (5 concurrent cost-adds at version 0, 5 concurrent votes at version 0) are the acceptance criteria — they should pass after the fix. Do NOT weaken or delete those tests to make them pass; the fix must make the actual behavior correct so the tests pass legitimately.
