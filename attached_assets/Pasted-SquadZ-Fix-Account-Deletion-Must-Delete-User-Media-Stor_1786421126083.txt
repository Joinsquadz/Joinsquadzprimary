SquadZ — Fix: Account Deletion Must Delete User Media (Storage + Backup) — Compliance Blocker

Context: the final pre-submission scan found that account deletion does NOT remove the user's media. This is a privacy-compliance blocker (GDPR/CCPA-style "delete my account = delete my data" expectation), especially for a social app handling user photos. The database records get deleted (the resurrection bug was fixed earlier), but the actual media files persist. Fix the media cleanup so deletion is genuinely complete.

The gaps (from the scan)
Live media objects in Supabase Storage are NOT deleted during account deletion.
The R2 backup copies of that media are not reconciled/removed.
Public avatars are not tracked/deleted consistently.
What to build

When a user deletes their account, in addition to the existing database cascade:

Delete their media from Supabase Storage — every object the user owns across all buckets in use (the private media bucket, the avatars bucket, and any others confirmed in use). Identify the user's objects reliably (by path/prefix convention or an ownership record — confirm how media ownership is actually tracked before implementing, and report it).
Public avatars: ensure the avatar bucket objects for the deleted user are removed consistently, not left orphaned.
R2 backup copies: decide and implement the right behavior for the backup. Two reasonable approaches — pick and justify:
(a) Delete the user's objects from the R2 backup as part of deletion, so "deleted" truly means gone everywhere, OR
(b) Let the backup retention naturally age them out, but document this clearly so it's a known, intentional behavior rather than an accidental gap. Given this is a privacy-deletion requirement, lean toward (a) — actually removing backup copies — unless there's a strong operational reason not to. Whatever you choose, it must be a deliberate, documented decision, not silent.
Important safety requirements for this fix
Deletion must be resilient: if a storage-delete call fails partway (e.g. some objects deleted, then an error), the account deletion should not be left in a broken half-state. Handle partial failures — either make it retryable, or ensure the DB cascade and storage cleanup are coordinated so a failure is recoverable and logged, not silent. Report through Sentry on failure (a deletion that silently half-completes is a real problem).
Do NOT delete other users' data: be precise about identifying only the deleting user's objects. A bug here that over-deletes would be catastrophic. The ownership-identification logic (step 1) must be exact — confirm it carefully and test it.
Do not touch the R2 restore-drill safety guards or the backup job itself beyond adding the deletion-cleanup path.
