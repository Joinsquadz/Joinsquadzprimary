## Part 1 — Privacy-isolation audit specific to Transaction pooler (do this first)

The earlier session-mode audit checked for `LISTEN`/`NOTIFY`, session-scoped advisory locks, and `SET` persistence — good, but reframe the same codebase search around this specific risk: **Transaction pooler reuses physical DB connections across different users' unrelated requests.** Anything that sets connection-level state and assumes it stays scoped to "this user's session" is a potential cross-user data leak under this pooling mode, not just a correctness bug.

Specifically check:
- Any `SET` (not `SET LOCAL`) statement anywhere in the codebase — `SET` persists on the physical connection beyond the current transaction; `SET LOCAL` is transaction-scoped and safe. If any `SET` (non-local) exists, it must be converted to `SET LOCAL` or removed, since under Transaction pooler it could leak into the next unrelated user's request on that same physical connection.
- Any place a raw DB client/connection object is cached, reused, or attached to a long-lived variable (e.g. a module-level singleton) outside the per-request lifecycle, rather than obtained fresh per request/transaction through the pool.
- Confirm the ORM/query builder in use (Drizzle) is issuing all queries through the pool per-request and not holding a connection open across requests for any user-scoped operation.
- Report explicitly: found anything, or clean. If anything is found, fix it as part of this same pass and add a regression test proving connection state doesn't leak between two simulated back-to-back requests from different users.

## Part 2 — Load-test tooling setup

1. Install a real load-testing tool in the project — **k6** is preferred (scriptable in JS, good for API load testing, no separate infra needed). If k6 isn't installable in this environment, use **Artillery** instead.
2. Write a load-test script covering the hot endpoints identified in the earlier scale-readiness pass: squad list, plan list, feed, notifications, and login/auth. Script should ramp concurrent virtual users from a low baseline up through at least 100, sustaining each step long enough to observe steady-state behavior (not just a burst).
3. The script must target a **real deployed instance URL**, not localhost — confirm what deployable staging target exists (or needs to be created) for this to run against. If no staging deployment currently exists separate from production, flag this clearly and stop before running anything destructive against production — this needs a safe target to run against, not a guess.
4. Do NOT run this against production data with real user accounts. Seed a set of disposable test accounts for the load test to use, clearly namespaced/identifiable so they can be cleaned up afterward, and confirm a cleanup step exists.
