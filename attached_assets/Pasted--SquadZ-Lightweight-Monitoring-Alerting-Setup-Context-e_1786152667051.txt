# SquadZ — Lightweight Monitoring & Alerting Setup

Context: everything tested so far (load tests, scale fixes) has been manually triggered and manually watched. There's no ongoing visibility into production health — if something degraded at 2am, nobody would know until a user complained. This prompt builds the minimum real monitoring needed to close that gap, without overbuilding.

Sentry and PostHog are already integrated in the app (crash/error capture and analytics respectively) — build on top of what exists rather than adding new tools unless genuinely necessary.

## Part 1 — DB connection pool usage visibility

1. Add a lightweight internal check (can be a scheduled interval, e.g. every 5 minutes, similar pattern to the existing engagement scanners) that queries current active connection count against the database (e.g. via `pg_stat_activity` or an equivalent lightweight query) and compares it to `DB_POOL_MAX` (currently 45) and the actual Supabase `max_connections` ceiling (currently 90 on Small tier, confirmed earlier in this project).
2. If usage crosses a reasonable warning threshold (e.g. 80% of `DB_POOL_MAX`), log a clear warning and report it through Sentry (as a warning-level event, not an error, so it doesn't get lost among real errors but also doesn't create alert fatigue).
3. Keep this cheap — a single lightweight query on an interval, not a heavy monitoring system.

## Part 2 — Response time / error rate visibility

1. Confirm whether Sentry's performance monitoring (transaction/latency tracking) is already enabled for this project, given Sentry is already integrated for error capture. Report what's currently configured.
2. If not already covered, add lightweight logging for requests that exceed a reasonable slow-response threshold (e.g. requests over 1-2 seconds) on the hottest endpoints (squads, events, feed, activity) — reported through Sentry as a warning, consistent with Part 1's approach, so slow-request trends are visible over time rather than only discoverable by manually running a load test.
3. Do not build a custom performance-monitoring system from scratch if Sentry already covers this — check first, extend only what's missing.

## Part 3 — A simple internal health snapshot

Build a minimal, auth-protected internal endpoint (or extend an existing admin/health route if one exists) that reports, in one place:
- Current DB connection count vs. pool max
- Recent error rate (last hour, from Sentry or application logs)
- Basic uptime/health confirmation

This is meant to be a 10-second glance, not a full dashboard — keep it simple.

## Part 4 — Report what requires manual dashboard setup (do not attempt to build these)

Report clearly, for the person to action manually, rather than attempting to automate:
- Whether Supabase's built-in usage/quota email alerts (storage, compute, connections approaching plan limits) are enabled at the organization level — this is a Supabase dashboard setting, not something to build in code.
- Whether Sentry has actual notification channels configured (email/Slack/etc.) for alerts to actually reach someone, not just be logged silently — also a dashboard-level setting.
- Confirm whether Supabase's daily backups (included on Pro, 7-day retention per the current plan) are actually enabled and a recent backup exists — check what's confirmable via Supabase's API/dashboard access if any, otherwise report that this needs manual verification in the Supabase dashboard's Backups section.

## Required for this pass
- Keep everything in Parts 1-3 lightweight and additive — no new paid services, no heavy new infrastructure, consistent with the DB_POOL_MAX and LISTEN/NOTIFY decisions made earlier in this project to avoid unnecessary complexity or cost.
- Regression tests for anything added; confirm existing test suite (972 API / 351 mobile) is unaffected.
- Part 4 should be a clear, actionable checklist handed back — not attempted in code.
