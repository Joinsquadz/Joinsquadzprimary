## Priority 1 — Migrate SSE pub/sub to Postgres LISTEN/NOTIFY

**Decision, locked (revised from an earlier draft of this task that specified Supabase Realtime)**: replace the process-local in-memory subscriber registries in `activityEvents.ts`, `feedEvents.ts`, `conversationUpdates.ts`, and `squadEvents.ts` with **Postgres LISTEN/NOTIFY**, not Supabase Realtime and not a new Redis dependency. Reasoning: LISTEN/NOTIFY is core Postgres functionality, portable to any Postgres host (Supabase, AWS RDS, self-hosted, anywhere) with zero vendor-specific code — this keeps the most likely-to-change piece of the stack portable at no extra cost, rather than adding a new Supabase-specific dependency.

**Important connection detail**: LISTEN/NOTIFY requires a persistent, held-open connection for the life of the listener — this is fundamentally incompatible with the Transaction pooler (port 6543), which returns connections to the pool after each transaction and would silently break the LISTEN session. Use a **separate, dedicated connection per server instance** (not per-user, not per-request — one per instance) via the **Session pooler (port 5432)** or a direct connection, held open for the process lifetime, entirely separate from the main `DB_POOL_MAX=45` transaction-pooled request-handling pool. This is a small, fixed number of extra connections (one or two per instance) and does not compete with the request-handling pool's budget.

Implementation approach:
- Each server instance establishes one dedicated long-lived LISTEN connection on startup, listening on a small set of broad channels (e.g. `squad_events`, `feed_events`, `conversation_events`, `activity_events` — one per domain, not one per squad/user/conversation; Postgres channels aren't meant to be created per-entity at scale).
- When an event fires on any instance (a squad update, new feed post, conversation message, activity item), issue a `NOTIFY` on the relevant channel with a compact JSON payload (Postgres NOTIFY payloads are capped at 8000 bytes — include only enough to identify and route the event, e.g. type + relevant IDs, not full event content; clients/instances needing full data can look it up).
- Each instance's LISTEN connection receives every NOTIFY on its subscribed channels and forwards the relevant ones to its own locally-connected SSE clients — same routing/visibility logic as the current in-process emit, just triggered by the NOTIFY callback instead of a direct function call.
- Add reconnection handling: if the dedicated LISTEN connection drops, reconnect and re-issue LISTEN for all channels rather than silently going deaf.
- Confirm this doesn't leak data across visibility boundaries — every instance receives every NOTIFY on a channel it's listening to (Postgres NOTIFY is broadcast-to-all-listeners by design), so the per-client filtering must happen in application code using the same access-check logic already used to decide SSE subscription eligibility today. Do not rely on channel scoping alone for access control.

Test: simulate two "instances" (two separate processes/connections, each with their own dedicated LISTEN connection) where an event fires on instance A — confirm a client connected via instance B's SSE handler receives it. This is the core correctness test this whole change exists for. Also test: kill and restart the dedicated LISTEN connection mid-run, confirm it reconnects and resumes receiving notifications.
